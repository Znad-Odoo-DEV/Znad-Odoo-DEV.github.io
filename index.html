Nudge, an AI companion inside Odoo

Press a shortcut on any Odoo screen and ask, in Arabic or English. Nudge sees the record you are on, knows how this database is set up, and works with your own rights, never beyond them. I designed and built it end to end: seven modules, three modes.

  • Ask. Talk mode

    Explains the screen you are on and walks you through it, with a pointer that goes to the field or button to use. Answers how Odoo works from the official documentation shipped with the module: 1,067 pages, searched in PostgreSQL, nothing fetched from outside.

  • Do. Agent mode

    Finds, creates and changes records and presses buttons with your rights, after a card that shows what will happen and waits for your yes. Many records go through one plan, tried first and undone so the card can say which will pass, with undo afterwards. Long work runs in the background; scheduled tasks are asked for in words.

  • Build. Developer mode

    Writes automation rules, server actions, designed email templates, fields, views and PDF reports. Each one is tried on a dummy record first, and everything it builds can be undone.

Approach

How the work gets done

Techno-functional means both halves of the job. I gather the requirements and push back on them, design the data model and the flows — then write the Python, XML, OWL and SQL that make them real. No handover gap between what was promised and what got built.

Most of my work starts with a process already running on spreadsheets or a quick configuration that has outgrown itself. I replace it with native modules: proper models, computed fields that recompute, security groups and multi-company record rules, and migration scripts so nothing is lost on the way over — while the business keeps running every day.

Correctness is the requirement, not a feature. Figures reconcile across every view, report and export; every change leaves an audit trail; access is governed by role and by company; and month-end closes without a spreadsheet on the side. A business system is judged in its second month, not in the demo.

Platform upgrade

Odoo 18 to 19, on a live production database

A live multi-company database running purchasing, inventory, projects, time off and payroll, moved a major version without a day of downtime and without moving the data by hand. Most of the work is what happens before and after the jump.

Read the case study
  1. 01

    Inventory first

    Crawl every menu and window action to find the ones that open nothing, list the models no group can actually read, and record what each custom model still holds — so nothing is deleted on a hunch.

  2. 02

    Prepare production, not staging

    The upgrade platform works from production's own nightly backup, so the preparation has to land there. Whatever blocks the jump is switched off rather than dropped, in SQL so a broken registry cannot stop it, and switched straight back on once the backup is taken.

  3. 03

    Port the modules

    Drop what 19 removed — numbercall on ir.cron, the version prefix that made a module unloadable — and follow the contract into hr.version. The version-specific parts are chosen at import time, so the same branch boots on 18 and on 19 and the rollback stays real until the last minute.

  4. 04

    Prove it, then open the doors

    The same inventory runs again on the upgraded database and is compared line by line with the one taken before: menus, actions, record counts and the figures that pay people. Nobody logs in until the two agree.

Method

How a change reaches a live database

These systems buy, store and pay. A wrong figure is not a bug report, it is somebody's order, stock balance or salary, so what follows is not process for its own sake. It is what makes a change to a running database safe to make.

Before production

Run it on a real database first

Every module change is installed and exercised on a local Odoo 19 with PostgreSQL before it is pushed, because the branch builds production directly. Claims about how the framework behaves are verified by running them, not by recollection.

That pass catches what a reading does not: a model absent from the registry because the manifest never declared it, a flag that flipped the wrong way when its value was cleared, a constraint that only fires on a non-working day. Each would have arrived in production as a failed build or a silently wrong number.

Tooling

Report first, write only when asked

A hundred-odd shell tools sit beside the modules, and every one reports by default. Writing is armed by an environment variable on the single run that needs it, so the copy in the repository is never the loaded one and no tool can change anything merely by being executed.

Anything that moves money or stock prices what it would move before it moves it, and names the people it would move it for. The figure worth arguing over is the one in the dry run, not the one in the audit afterwards.

Blast radius

A fix that cannot reach a paid month

When a rule changes, the days it governs are bounded in the code rather than in anybody's intention. A repair carries the date it takes effect from, and rows before it keep what they were given — because approving something backdated next month must not rewrite attendance that has already been paid.

The same care runs upward. A payslip that has been issued stops listening to the employee master; one that has been paid stops listening to everything. Recalculating a closed month is not a recalculation, it is a change to a settled account. A posted journal entry or a done stock move is the same: reversed, never recomputed.

Diagnosis

Measure the thing, not its shadow

A count is easy to read and easy to misread. Filtering on a column that a background job fills measures how far that job has got, not what the rule would do — and the two are indistinguishable, because both answers are numbers.

So a probe resolves what it is testing the way the code resolves it, and says which of the possible causes actually holds. Losing an exemption is not the same as becoming absent. A missing link is not a missing person.
